## 1 开发过程

### 1.1 版本一——AI 生成版

版本一几乎没有人工设计输入。我只给 AI 编程代理一句高层指令——“为一个 AI / 计算机专业的学生做一个个人主页”，随后刻意让它自行决定几乎全部设计与实现方案。

代理一次生成就交出了一个完整可用的单页站点：

- **结构**：固定顶部导航栏（移动端折叠为汉堡菜单），下接 Hero、关于、技能、项目四个区块，以及联系页脚；全部由 `index.html`、`style.css`、`script.js` 三个文件实现。
- **视觉风格**：浅色卡片式布局，语气轻松随意（章节标题使用 emoji，文案如“trying to figure out why my model's loss isn't decreasing”）。
- **实现步骤**：代理自行选择技术栈（原生 HTML/CSS/JS、Google Fonts 的 `Inter`），生成配色与间距体系，编写响应式断点，甚至自行虚构了项目卡片的占位内容。

我在这一阶段的参与仅限于查看输出，并把页面发布到 `AI-generated-page` 仓库、开启 GitHub Pages。我没有提供任何设计规格；布局、配色、字体、文案与文件组织，全部由 AI 决定。

### 1.2 版本二——人工引导版（详细的人工规格）

版本二的做法完全相反：我先确定自己要什么，再逐步向 AI 下达指令，并在真实浏览器中检查每一轮改动。我的规格覆盖布局、内容、视觉风格与功能四方面：

- **布局**：固定左侧边栏（头像、姓名、角色、导航、主题与语言按钮），右侧为居中的主内容列；Hero 区使用打字机效果，其后是按编号排列的章节（01 关于 / 02 技术栈 / 03 近期竞赛 / 04 科研项目 / 05 联系），采用开发者作品集的常见组织方式，而不是通用模板。
- **视觉风格**：由 CSS 自定义属性（`--bg`、`--accent`、`--border` 等）驱动的两套完整主题——默认冷色深色主题与暖米色浅色主题；章节编号与按钮使用等宽字体 `JetBrains Mono` 点缀；主标题为带闪烁光标的打字机文字。竞赛区刻意打破规整网格：卡片略微旋转，用“胶带”压住，并以手写体（`Caveat`）批注，像钉在板子上的便条。
- **内容**：只使用真实个人信息——我的真实教育经历（山东农业大学数据科学本科、宁波诺丁汉大学 ECCE 硕士），真实研究兴趣（目标检测、基于大语言模型的车辆控制），三项可核验成绩的竞赛（天池表格理解比赛 79.40/100、灵机具身智能挑战赛 56.8% 成功率、Kaggle Name That LLM 0.305 平衡准确率），以及 CSDN 博客的实时数据（51 篇原创、1.6 万余次阅读、199 次收藏），而不是 AI 虚构的占位内容。
- **功能**：深色/浅色主题切换与中英文切换，二者均持久化到 `localStorage`；技能条只在滚动进入视口时才播放动画（由 `IntersectionObserver` 触发，每类技能一个观察器）。

因为我把需求写得很细，开发过程从“一次生成”变成了迭代循环。最有启发性的一轮是浏览器测试时发现的 bug：点击主题按钮后没有任何反应，技能条也始终不播放动画。浏览器控制台显示 `ReferenceError: Cannot access 'themeBtn' before initialization`——这是一个暂时性死区（temporal dead zone，TDZ）错误。一个刷新翻译的函数在 `const themeBtn` 声明求值之前就调用了 `updateThemeBtn()`，而异常中断了脚本后续执行，导致此后注册的所有监听器（主题切换、滚动观察器）都静默地没有绑定。把声明移到第一次函数调用之前，两个症状同时消失。这个 bug 让我对 JavaScript 执行顺序的理解超过此前任何教程，而它之所以暴露，只是因为我亲手在浏览器里测了，而不是直接相信生成的代码。

后续迭代全部由我自己查看渲染结果驱动：第一版浅色主题偏“医院白”，于是重做成暖米色调；增加完整的中英双语层（每个界面文案都是双语字典中的一个键），并硬性要求英文视图不得出现任何中文字符；把头像字母换成裁成 160 px 见方的真实照片；用 `max(280px, calc((100% - 900px) / 2))` 重新居中内容列，使其在任意视口宽度下都保持平衡；把探索性的 LLM 车辆项目卡片移到科研列表末尾；竞赛卡片原本平淡，在觉得缺乏个人感之后重新设计为手绘风格。每次改动都先在本地（`python -m http.server`）于两种主题、两种语言下验证，再推送到 GitHub Pages，并用 `style.css?v=9` 这类查询串强制浏览器加载最新文件。

## 2 对比与评估

| 维度     | 版本一（AI 生成）                                            | 版本二（人工引导）                                                                             |
| -------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 设计     | 通用卡片模板，观感尚可但可替换性强                           | 定制的双主题视觉体系（CSS 变量、侧边栏、等宽字体点缀、手绘竞赛卡片），与事先声明的风格目标一致 |
| 内容     | 部分由 AI 虚构（“I'm an AI & CS Student”，并非我的真实专业） | 可核验的真实数据：真实教育经历、三项真实竞赛成绩、真实博客数据                                 |
| 功能     | 静态内容加移动端菜单                                         | 主题与语言切换并持久化、滚动触发动画、打字机效果                                               |
| 开发速度 | 一次提示、一次生成，最快得到可用站点                         | 跨多次会话的多轮迭代                                                                           |
| 调试投入 | 几乎为零                                                     | 需要真实调试（TDZ 错误），借助浏览器控制台定位                                                 |
| 人的参与 | 低：只做查看与发布                                           | 高：定义布局、内容、风格与行为，逐项在浏览器中检查，并决定每次迭代                             |

**对比说明了什么。** 版本一说明了一句提示能走多远：结果完整、响应式、可以直接发布，对一次性页面而言已经够用。它的弱点是真实性——AI 用听起来合理的通用内容填补了它不知道的信息，于是页面描述的是一个并不完全存在的学生。

版本二把我的角色从“审阅者”变成了“导演”。代价是真实的：更多轮会话、一个需要真正定位的 bug、以及每个双语文案都要仔细核对（每个界面文案都是双语字典中的一个键，翻译表本身必须保持一致）。收益是一个真正属于我的页面：事实正确、视觉识别由我选定、功能由我指定。就人的参与程度而言，两个版本处在两个极端，而质量差距几乎与参与程度成正比。

版本二最重要的技术教训是：**生成的代码不等于被验证过的代码**。TDZ 这个 bug 不产生任何构建警告，只表现为界面静默失效；如果我不亲自打开浏览器控制台，就永远发现不了它。

## 3 个人反思

V1 是我让 AI 一次性生成的。做完之后我的第一反应不是好看不好看，而是这个东西太假了。AI 自己填了一套和我完全不符的专业身份，还造了一些没发生过的经历。我对这种错误一直很敏感，以前实习的时候，在没有自动化测试的阶段，我经常能发现测试漏掉的问题。但我没有改 V1，留着它作为一个原始样本，因为它本来就代表一种完全不经过人的状态。

V1 看起来很完整，什么板块都有，配色统一，还有动画。但正因为它太完整了，反而一眼就能看出没花什么心思。如果把这样的页面当成个人简历挂出去，没人会觉得你是个值得认真对待的人。这件事让我觉得，AI 生成内容最大的问题不是它做得不好，而是它没有动机去做对。它不会为内容的真假负责，也不会为这个页面挂出去之后别人怎么看你负责。这是我从 V1 里学到的第一件事：在 AI 辅助开发里，**负责**这件事只能落在人身上，而且没有任何环节可以替你承担。

我实习做了半年产品经理。那段经历让我对网页有一些基本的感觉，但并不深。我更多做的是页面之间的关系、功能的拆分，还有写文档。审美是在给甲方做项目的过程中慢慢磨出来的，不是看什么书看来的。我以前也想过一个好网页到底长什么样，去读产品经理的书，后来发现那些审美已经是十年前的了。现在的网页看着和十年前差别不大，但内里的东西厚了很多。不过说这些也没什么用，因为做这行做久了会发现，审美最后都会流向老板和甲方，我大多数时候只是个转递需求的人。只有人类共通的那些东西，比如对称、居中、留白，是不太会变的。

这次作业里我站在了甲方的位置上。我对 AI 说我想要什么，它就去做，像当年的我一样。差别是它几乎能满足我的全部要求，而我当年不仅会出错，还会跟甲方顶嘴。这件事有意思的地方在于，当实现变得很容易，我反而不知道自己到底要什么了。AI 不会反驳我，所以每一个需求是不是合理，都得我自己判断。以前做产品经理的时候，我还可以把判断的一部分推给甲方，说这是你要的。但这次没有甲方，我就是甲方，**判断**没有地方可以推。

V1 做完之后老师一直说这个东西至少得有用。这句话让我改了标准。我原来想做一份满分作业，后来开始想，这个网页我以后愿不愿意拿出来用。相比一段只能写进简历的经历，我更想做一个当下就能用的东西。V2 就是在这个标准下做的。我希望它能被我挂到不同的地方，哪怕只是给人留下一个还不错的印象就够了。这个转变本身也说明了，AI 能帮你实现功能，但不能帮你**定义**什么叫有用。“满分”和“有用”是两个完全不同的验收标准，这个标准只能由我来定。

做 V2 的过程里我有过几次很明确的取舍，正好对应上面这三件事。

一次是加特效。我加了极光背景、头像旋转的光环，想展示一点技术能力，也想让页面看起来更专业。但实际效果出来我马上就回滚了。它太浮了，像在告诉别人“快看我会做动画”，而不是在介绍我这个人。我现在在学术阶段，如果页面做得太花哨，别人会觉得我是个设计师而不是做学术的。文字和履历其实就可以说明很多问题，只是现在的我还没到那个程度，还需要一点设计来撑一下。删减也是设计，这个道理我以前在工作里就知道，但只有自己亲手删的时候才真的有感觉。留白不是空，是让该被看到的东西被看到。AI 倾向于加满，因为加满看起来更像“做了事”，但设计的**判断**恰恰在于知道什么时候不加。

一次是主题切换。我一开始只说要一个浅色深色切换的按钮，AI 做出来的是冷暖色的变化，和我想要的完全不是一回事。这让我意识到，提需求和定义标准是两件事。“有一个按钮”和“按钮符合用户对浅色深色的预期”中间差了很远。以前我做产品经理的时候经常把这两件事混在一起，这次算是亲身体会了一次。AI 能执行明确的指令，但对隐含的、默认的预期是没有概念的。这部分必须由人在一开始就**定义**清楚，否则做得再快也是错的。

还有一次是线上更新。代码改完、push 成功、GitHub 显示部署成功，但我打开页面看到的还是旧内容。我一度以为修改没生效，后来才发现是浏览器缓存。功能也不是部署完就算了，每一项都得逐项点开验证。这让我觉得，**负责**不只是写代码的时候不造假，还包括上线之后确认用户看到的确实是你想给的东西。AI 不会帮你做这个确认。

整个 V2 的节奏和我做别的事差不多。前期没什么感觉，中期定下方向，中后期看各种风格找参考，最后阶段几乎都在改细节。AI 完成了大量基础工作，但它的局限也很明显。它不太能判断什么样的设计让人眼觉得舒服，有时候它完成了我提的局部要求，却没有考虑整体是不是协调。这部分只能我来。我没有因为这次作业就觉得自己掌握了网页开发，但也不会为依赖 AI 觉得不好意思。能用工具是能力，知道工具在哪一步停下来，也是能力。

V2 比 V1 好，是因为它有更多真实的资料、更多修改的时间和更多反馈。这不能说明有人工参与就一定更好，只能说明在这个具体的任务里，我做的判断起了作用。中间我还试过美式风格，改了很多次，最后只在比赛那块留了一点点，因为不同风格硬拼在一起会很突兀。美日中的界面审美差别很大，这也许是个可以专门研究的方向，但不是这次作业要解决的。

做完 V1 和 V2，我觉得这次作业最实在的收获，是把人在 AI 辅助开发里的角色想清楚了。以前写代码的时候，实现本身就够难，人的精力大部分被实现占走了，反而容易忽略别的。现在实现被 AI 接走了一部分，剩下的三件事就凸显出来了：**定义**做什么、**判断**做得对不对、**负责**结果。这三件事以前也在人身上，只是没这么显眼。这次作业让我第一次清楚地感觉到，它们才是我真正不可替代的部分。
